| C1 | Test techniques help the tester decide what to test (test analysis) and how to test it (test design). They help build a "relatively small, but sufficient, set of test cases in a systematic way". | "Test techniques help to develop a relatively small, but sufficient, set of test cases in a systematic way." | S1 p38 (section 4.1) | |
| C2 | The syllabus classifies techniques as black-box, white-box and experience-based. | "test techniques are classified as black-box, white-box, and experience-based" | S1 p38 | |
| C3 | Black-box (specification-based) techniques are based on the specified behavior of the test object without reference to its internal structure. Test cases stay useful if the implementation changes but the required behavior does not. | "Black-box test techniques (also known as specification-based techniques) are based on an analysis of the specified behavior of the test object without reference to its internal structure." | S1 p38 | Why they suit Claude working from a requirement or Jira text. |
| C4 | The four common black-box techniques in the syllabus are equivalence partitioning, boundary value analysis, decision table testing and state transition testing. | list in section 4.2 | S1 p38 | |
| C5 | Equivalence partitioning (EP) divides data into partitions, expecting all elements of a partition to be processed the same way. One test per partition is enough. | "EP divides data into partitions (known as equivalence partitions) based on the expectation that all the elements of a given partition are to be processed in the same way by the test object." / "one test for each partition is sufficient" | S1 p38 | |
| C6 | Partitions can be made for any data element: inputs, outputs, configuration items, internal values, time-related values, interface parameters. They can be continuous or discrete, ordered or unordered, finite or infinite. They must not overlap and must be non-empty. | "The partitions must not overlap and must be non-empty sets." | S1 p38 | |
| C7 | A valid partition holds valid values. An invalid partition holds invalid values. Definitions of "valid" vary by team (e.g. "should be processed" vs "specification defines their processing"). | "A partition containing valid values is called a valid partition." | S1 p39 | |
| C8 | EP coverage items are the partitions. 100% coverage needs every partition, including invalid ones, covered at least once. Coverage = partitions exercised ÷ total partitions, as a percentage. | "Coverage is measured as the number of partitions exercised by at least one test case, divided by the total number of identified partitions" | S1 p39 | |
| C9 | With several parameters, the simplest criterion is Each Choice coverage: every partition of every set at least once. It ignores combinations of partitions. | "Each Choice coverage does not take into account combinations of partitions." | S1 p39 | Leads into pairwise (C23 to C26). |
| C10 | Boundary value analysis (BVA) exercises the boundaries of equivalence partitions. It can only be used for ordered partitions. The minimum and maximum of a partition are its boundary values. | "Therefore, BVA can only be used for ordered partitions. The minimum and maximum values of a partition are its boundary values." | S1 p39 | |
| C11 | BVA focuses on boundaries because developers are more likely to err there. Typical defects: boundaries misplaced above or below the intended position, or omitted. | "developers are more likely to make errors with these boundary values" | S1 p39 | |
| C12 | 2-value BVA: for each boundary value there are two coverage items, the boundary value and its closest neighbor in the adjacent partition. | "this boundary value and its closest neighbor belonging to the adjacent partition" | S1 p39 | Example for a field valid 1 to 100: boundary 100 and neighbor 101; boundary 1 and neighbor 0. (Example is the writer's own arithmetic.) |
| C13 | 3-value BVA: for each boundary value there are three coverage items, the boundary value and both its neighbors. Some coverage items are then not boundary values. | "this boundary value and both its neighbors" | S1 p39 | Example for valid 1 to 100: 0, 1, 2 and 99, 100, 101. |
| C14 | 3-value BVA is more rigorous. Example: `if (x ≤ 10)` wrongly coded as `if (x = 10)`: 2-value data (x = 10, x = 11) cannot detect it, but x = 9 from 3-value BVA is likely to. | "no test data derived from the 2-value BVA (x = 10, x = 11) can detect the defect. However, x = 9, derived from the 3-value BVA, is likely to detect it." | S1 p39 | Best teaching example. |
| C15 | BVA coverage = boundary values (or values plus neighbors for 3-value) exercised ÷ total, as a percentage. | "Coverage is measured as the number of boundary values that were exercised, divided by the total number of identified boundary values" | S1 p39 | |
| C16 | Decision tables test requirements that say how combinations of conditions give different outcomes. They record complex logic such as business rules. | "Decision tables are an effective way of recording complex logic, such as business rules." | S1 p40 | |
| C17 | Rows are conditions and actions. Each column is a decision rule: one unique combination of conditions with its actions. Limited-entry tables use Boolean values. Extended-entry tables allow multiple values (ranges, partitions, discrete values). | "Each column corresponds to a decision rule that defines a unique combination of conditions, along with the associated actions." | S1 p40 | |
| C18 | Notation: conditions "T" (true), "F" (false), "–" (irrelevant for the outcome), "N/A" (infeasible for the rule). Actions: "X" (should occur), blank (should not occur). | exact notation list | S1 p40 | |
| C19 | A full table covers every combination. Delete columns with infeasible combinations to simplify. Merge columns where some conditions do not affect the outcome to minimize. | "The table can also be minimized by merging columns, in which some conditions do not affect the outcome, into a single column." | S1 p40 | |
| C20 | Decision table coverage items are the columns with feasible combinations. Coverage = exercised columns ÷ feasible columns. The number of rules grows exponentially with the number of conditions. Use a minimized table or a risk-based approach if there are many. | "the number of rules grows exponentially with the number of conditions" / "a minimized decision table or a risk-based approach may be used" | S1 p40 | Strength: finds gaps or contradictions in the requirements. Good for requirement review. |
| C21 | State transition testing: a diagram shows states and valid transitions. A transition is started by an event, optionally with a guard condition. Label syntax: `event [guard condition] / action`. | "The common transition labeling syntax is as follows: “event [guard condition] / action”." | S1 p40 | |
| C22 | A state table is equivalent to the diagram: rows are states, columns are events (with guards), cells hold target state and actions. Unlike the diagram it shows invalid transitions as empty cells. | "the state table explicitly shows invalid transitions, which are represented by empty cells" | S1 p40 | |
| C23 | A state-based test case is a sequence of events that gives a sequence of state changes. One test case usually covers several transitions. | "One test case may, and usually will, cover several transitions between states." | S1 p40 | |
| C24 | Three state-transition coverage criteria: all states (visit every state); valid transitions, also called 0-switch (exercise every valid transition); all transitions (exercise every valid transition and attempt every invalid one). Full all-transitions coverage includes the other two. | "Achieving full all transitions coverage guarantees both full all states coverage and full valid transitions coverage and should be a minimum requirement for mission and safety-critical software." | S1 p40 to p41 | Valid transitions coverage is "the most widely used". |
| C25 | In all-transitions coverage, test only one invalid transition per test case. This avoids fault masking (one defect hiding another). | "Testing only one invalid transition in a single test case helps to avoid fault masking" | S1 p41 | Prompt rule for Claude. |
| C26 | Pairwise testing (combinatorial): combinatorial testing explores combinations of parameter values to reveal interaction failures. Pairwise coverage has coverage items that are pairs of parameter-value pairs for any two parameters. | "Pairwise coverage, in which coverage items are pairs of parameter-value pairs for any two parameters." | S2 p30 | Advanced Level (Test Analyst) syllabus, not Foundation. Say so on the page. |
| C27 | A parameter-value pair is a parameter and its value, e.g. `(color, red)`. | "A specific parameter-value pair consists of a parameter and its value (e.g., ’(color, red)’)." | S2 p30 | |
| C28 | Tools can generate pairwise coverage items. Finding a minimal set of test cases that gives pairwise coverage is generally difficult. | "Tools are available for generating coverage items. However, finding a minimal set of test cases achieving pairwise coverage is generally difficult." | S2 p31 | Reason to have Claude drive a generator tool or script, not hand-build the set. Do not claim Claude's hand-built sets are minimal. |
| C29 | For parameters with many values, apply EP first to reduce values. A classification tree or feature model helps capture parameters and values. Constraints, known-problem combinations and invalid combinations change the final count. | "For parameters with many values, EP may first be applied to reduce this number" | S2 p31 | |
| C30 | Base choice coverage: choose a base parameter-value pair for each parameter. The base coverage item combines them. Further items replace one base value at a time with each non-base value. | "Subsequent coverage items are created from the base coverage item for each parameter by replacing its base parameter-value pair with each non-base value." | S2 p31 | Cheaper alternative to pairwise. |
| C31 | Rationale: not every parameter contributes to a failure. Most failures come from a single value or from interactions between a small number of parameters. In a limited study, about 97% of failures were caused by only one or two interacting conditions. | "about 97% of failures are caused by only one or two interacting conditions" | S2 p31 (cites D. Kuhn et al., 2004) | Say "in a limited study cited by the syllabus". Do not generalize. |
| C32 | Glossary (v2.3): pairwise testing is "A black box test design technique in which test cases are designed to execute all possible discrete combinations of each pair of input parameters." | exact quote | S3 | Matches C26 in meaning. 2014 wording. |
| C33 | Glossary (v2.3): combinatorial testing is a means to find a suitable subset of combinations to reach a predetermined coverage level when an object has several parameters with several values each, which gives more combinations than can be tested in the time allowed. | "which gives rise to more combinations than are feasible to test in the time allowed" | S3 | |
| C34 | Glossary (v2.3): n-wise testing designs test cases to execute all possible discrete combinations of any set of n input parameters. Pairwise is n = 2. | "all possible discrete combinations of any set of n input parameters" | S3 | |
| C35 | Experience-based techniques use the knowledge and experience of testers. Their effectiveness depends heavily on the tester's skills. They can find defects that black-box and white-box techniques miss, so they are complementary. | "experience-based test techniques are complementary to the black-box and white-box test techniques" | S1 p38 | |
| C36 | The syllabus names three experience-based techniques: error guessing, exploratory testing, checklist-based testing. | list in section 4.4 | S1 p42 | |
| C37 | Error guessing anticipates errors, defects and failures from the tester's knowledge: how the application has worked in the past, the errors developers tend to make, failures in similar applications. Defects can relate to input, output, logic, computation, interfaces or data. | "Error guessing is a technique used to anticipate the occurrence of errors, defects, and failures, based on the tester’s knowledge" | S1 p42 to p43 | |
| C38 | Fault attacks are a methodical way to do error guessing: build a list of possible errors and design tests that expose them. Lists come from experience, defect data, or common knowledge of why software fails. | "Fault attacks are a methodical approach to the implementation of error guessing." | S1 p43 | Claude can propose the list; the tester decides which apply. |
| C39 | Exploratory testing: tests are designed, executed and evaluated at the same time while the tester learns about the test object. It can use session-based testing: a time-box, a test charter, a debrief. | "tests are simultaneously designed, executed, and evaluated while the tester learns about the test object" | S1 p43 | |
| C40 | Exploratory testing is useful when specifications are few or inadequate or time is short. It complements formal techniques and can use other techniques such as EP. It is more effective with an experienced tester. | "Exploratory testing is useful when there are few or inadequate specifications or there is significant time pressure on the testing." | S1 p43 | |
| C41 | Checklist-based testing: the tester designs and runs tests to cover conditions from a checklist. Items are often questions and should be checkable separately and directly. Checklists should not hold items that can be checked automatically. Update them from defect analysis. | "Checklists should not contain items that can be checked automatically, items better suited as entry/exit criteria, or items that are too general" | S1 p43 to p44 | |
| C42 | Acceptance criteria are the conditions an implementation must meet to be accepted. They can be viewed as the test conditions. Two common formats: scenario-oriented (Given/When/Then) and rule-oriented (bullet list or input-output table). | "acceptance criteria may be viewed as the test conditions that should be exercised by the tests" | S1 p44 to p45 | Link requirement review to test conditions. |
| C43 | ATDD (acceptance test-driven development) creates test cases before implementing the story. Test cases can be run manually or automated. Techniques from 4.2 to 4.4 apply. Order: positive cases first, then negative, then non-functional. | "ATDD is a test-first approach" / "Typically, the first test cases are positive" | S1 p45 | |

## Page outline
- ## What test design is — techniques give a small but sufficient set of cases; black-box, white-box, experience-based (C1 to C4, C35). Why black-box techniques fit AI work from a requirement text (C3). Cite ISTQB CTFL v4.0 (and say the Foundation syllabus is the source).
- ## How to work with Claude on test design — the loop: give the requirement, name the technique, ask for the model first (partitions, table, diagram) then the cases, review the model, then generate (C1, C48). Rule: ask Claude to show the model (partition list, decision table, state table) so a human can check it before any test code. Own framing; no source for "model first" beyond S1 text. Also ask for a technique tag on each case.
- ## Equivalence partitioning — definition, valid/invalid, Each Choice coverage, coverage formula (C5 to C9). Example: password length field. Prompt: "List the partitions for each input in @spec. Mark valid and invalid. Give one test per partition. Report Each Choice coverage."
- ## Boundary value analysis — only ordered partitions; 2-value vs 3-value with the `x ≤ 10` example (C10 to C15). Prompt: "Use 3-value BVA. For each boundary, give the value and both neighbors." Callout: a table 2-value vs 3-value for range 1 to 100 (writer computes; mark as example arithmetic).
- ## Decision tables — conditions and actions as rows, rules as columns, notation T F – N/A X, limited vs extended entry, minimize, coverage = feasible columns, exponential growth, finds gaps in requirements (C16 to C20). QA scenario: discount or leave-approval rules. Prompt: "Build a limited-entry decision table from @spec. Mark infeasible combinations N/A. Tell me which rules the spec does not define."
- ## State transition testing — diagram, `event [guard] / action`, state table with empty cells for invalid transitions, three coverage criteria, one invalid transition per test (C21 to C25). QA scenario: order or ticket lifecycle (Jira status workflow). Prompt: "Draw the state table. Give tests for all valid transitions, and one test per invalid transition."
- ## Pairwise testing — interaction failures, pair coverage, tools needed, EP first, base choice, 97% limited study, source level (CTAL-TA, not CTFL) (C26 to C34). QA scenario: browser × OS × role × locale. Prompt: have Claude write or run a pairwise generator script and show the pairs-covered count. Warn: do not accept a hand-made "minimal" set (C28).
- ## Experience-based techniques — error guessing and fault attacks, exploratory testing with charters, checklists (C35 to C41). Claude proposes charters and lists; the tester runs and judges. Also acceptance criteria and ATDD as input for requirement review (C42, C43).
- ## From designed cases to automated tests — give Claude the table or case list and the existing test style; ask for tests that match the style and run them (C46 to C48). Data-driven loop for decision-table columns and BVA values (C53). Playwright Test Agents: planner → generator → healer (C50 to C52); link to the Playwright page. Save the workflow as a `/test-design` skill (C49). Guard: "do not change production code to make a test pass" (from Prompting page, C37 there).
