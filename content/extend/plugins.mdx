# Plugins & Marketplaces

A plugin packs skills, subagents, hooks, and MCP servers into one install. This page shows how to find, install, and review plugins, what the Superpowers plugin really is, and how a QA team can share its own setup through a small marketplace.

<PageMeta />

## What a plugin bundles

A Claude Code plugin is a directory of skills, agents, hooks, MCP servers, or other components that Claude Code installs and loads as one unit. <Cite n={1} /> It can contain: <Cite n={1} />

- Skills
- Agents (subagents)
- Hooks
- A hooks module (a "mod")
- MCP servers

The manifest, `.claude-plugin/plugin.json`, gives the plugin its name. <Cite n={1} /> A plugin skill runs with the plugin name in front, for example `/my-plugin:review`. <Cite n={1} />

Example: a QA team plugin.

```text
qa-toolkit/
├── .claude-plugin/
│   └── plugin.json          ← name: "qa-toolkit"
├── skills/
│   ├── find-bug/SKILL.md     ← /qa-toolkit:find-bug
│   └── test-design/SKILL.md
├── agents/
│   ├── qa-agent.md
│   └── sdet-agent.md
├── hooks/
│   └── hooks.json           ← protect .env and migrations
└── .mcp.json                ← Jira and test database servers
```

Plugin subagents ignore the `hooks`, `mcpServers`, and `permissionMode` frontmatter fields. <Cite n={2} /> So in a plugin, put the hooks in `hooks/hooks.json` and the servers in `.mcp.json`.

### Plugin or loose files?

- Use a plugin when you want several skills, subagents, hooks, or MCP servers packaged as one unit, when you share a setup with a team, or when you publish versioned releases. <Cite n={1} />
- Skills, subagents, hooks, and MCP servers also work without a plugin. <Cite n={1} /> For one project, files in `.claude/` are enough. See [Settings & the .claude Folder](/configure/settings/).
- An enabled plugin is part of every session, not only the sessions where you use it. The names and descriptions of its skills and agents are in context on each turn. <Cite n={1} />
- `claude plugin details <name>` shows a plugin's components and its projected token cost. <Cite n={1} /> Plugins in Anthropic's official marketplace show a **Context cost** estimate in `/plugin`. <Cite n={1} />

## Marketplaces

A marketplace is a repository or directory with a `.claude-plugin/marketplace.json` file. The file lists plugins and where to get each one. It is a catalog, not a hosted store. <Cite n={1} />

Anthropic runs three general marketplaces: <Cite n={3} />

| Marketplace | Name | Repository |
|---|---|---|
| Official | `claude-plugins-official` | `anthropics/claude-plugins-official` <Cite n={3} /> |
| Community | `claude-community` | `anthropics/claude-plugins-community` <Cite n={3} /> |
| Demo | `claude-code-plugins` | `anthropics/claude-code` <Cite n={3} /> |

- Claude Code adds the official marketplace the first time you start an interactive terminal session, unless a managed policy or `CLAUDE_CODE_DISABLE_OFFICIAL_MARKETPLACE_AUTOINSTALL` blocks it. <Cite n={3} />
- Most plugins in the official marketplace come from partners and other authors, not from Anthropic. <Cite n={3} />
- Anthropic does not review third-party marketplaces. <Cite n={3} /> Claude Code accepts the official and community names only for marketplaces from `github.com/anthropics/` repositories, so a third-party marketplace cannot present itself as an Anthropic one. <Cite n={4} />
- A plugin marketplace is not Claude Marketplace (claude.com/marketplace). You cannot add that website with `/plugin marketplace add`. <Cite n={1} />

<Callout type="warning" title="Community directory sites">

Websites that list thousands of plugins, skills, and MCP servers are community projects. They have no official standing, and a high install count is not a review. Read the plugin before you install it. See [Review before you install](#review-before-you-install).

</Callout>

## Install and manage

### In a session

Run `/plugin` to open the plugin menu. The **Discover** tab lists the plugins that you can install. <Cite n={5} /> You can also pass a subcommand such as `list`, `install`, `enable`, or `disable`. <Cite n={6} />

```text
/plugin install commit-commands@claude-plugins-official
```

In a session, this command does not install at once. It opens the plugin's details in the `/plugin` panel, so that you can review it and choose a scope first. <Cite n={5} />

To add a marketplace, run `/plugin marketplace add <source>`. <Cite n={5} /> The source can be: <Cite n={5} />

- A GitHub repository, `owner/repo`. Add `#ref` to pin a branch or tag.
- A git URL.
- A local path that starts with `./`.
- The `https://` URL of a hosted `marketplace.json`.

`/plugin market` is a shorter form of `/plugin marketplace`. <Cite n={5} /> Run `/reload-plugins` to apply plugin changes in a running session. <Cite n={5} />

### From the shell

| Command | What it does |
|---|---|
| `claude plugin install <plugin>@<marketplace>` | Installs a plugin. `--scope` takes `user`, `project`, or `local`. The default is `user`. <Cite n={7} /> |
| `claude plugin uninstall <plugin>` | Removes a plugin. Use the `--scope` that you installed it at. <Cite n={4} /> |
| `claude plugin list` | Lists installed plugins. `--json` gives machine-readable output. <Cite n={7} /> |
| `claude plugin details <name>` | Shows the components and the projected token cost. <Cite n={1} /> |
| `claude plugin validate <path>` | Checks a plugin or marketplace manifest. `--strict` treats warnings as errors, for CI. <Cite n={7} /> |
| `claude plugin update <plugin>@<marketplace>` | Updates one plugin. No command updates every plugin at once. <Cite n={5} /> |
| `claude plugin marketplace list` | Lists marketplaces. `update <name>` and `remove <name>` also work. <Cite n={5} /> |

- Removing a marketplace uninstalls its plugins. <Cite n={5} />
- In a `claude -p` run, `/plugin` does not run. Use the `claude plugin` commands instead. Plugins that you already installed still load. <Cite n={5} />
- `--plugin-dir <path>` loads a plugin from a folder for one session, with no marketplace. <Cite n={1} />

### Scopes

| Scope | Who gets it | Stored in |
|---|---|---|
| User | You, in all your projects | `~/.claude/settings.json` <Cite n={5} /> |
| Project | Everyone on the repository | `.claude/settings.json` <Cite n={5} /> |
| Local | You, in this repository | `.claude/settings.local.json` <Cite n={5} /> |

If a plugin is set at more than one scope, local overrides project, and project overrides user. <Cite n={5} />

A committed project-scope entry turns the plugin on for your teammates, but it does not download it to their machines. <Cite n={5} /> Each tester runs this one time: <Cite n={5} />

```bash
claude plugin install qa-toolkit@qa-team-plugins --scope project
```

### Updates

Auto-update is on by default for `claude-plugins-official`. It is off by default for every other marketplace. <Cite n={5} /> An update can change files that you already reviewed. <Cite n={4} /> Review the plugin again after an update.

## Review before you install

<Callout type="danger" title="A plugin runs code as you">

A plugin that you install can run any code on your machine with your user privileges. <Cite n={4} /> Permission rules and the sandbox cover Claude's tool calls, not the code that a plugin runs by itself. Claude Code runs hooks, monitors, MCP servers, and LSP servers outside the sandbox. <Cite n={4} />

</Callout>

A plugin can run hooks (shell commands), monitors, mods (JavaScript), MCP and LSP servers, and the files in its `bin/` folder, which goes on your `PATH`. Its skills, commands, and agents enter Claude's context as instructions. <Cite n={4} />

The docs give these review steps: <Cite n={4} />

1. Run `claude plugin marketplace list` to see where the marketplace comes from.
2. Read the **Will install** pane in `/plugin`.
3. Read `hooks/hooks.json`, `.mcp.json`, and every file in `bin/`. The **Will install** pane shows that a hook exists, but not what it runs. <Cite n={4} />
4. Run `claude --plugin-dir <dir> plugin details <name>`.

A marketplace's name tells you who publishes the catalog, not what each plugin in it does. Review a third-party plugin from any marketplace. <Cite n={4} /> If you no longer trust a plugin, uninstall it with the scope that you installed it at. If you do not trust the owner, remove the marketplace too. <Cite n={4} />

## Example: the Superpowers plugin

### What it is

Superpowers is a plugin in the official marketplace. Its entry says: "Superpowers teaches Claude brainstorming, subagent driven development with built in code review, systematic debugging, and red/green TDD." <Cite n={8} /> The README calls it "a complete software development methodology for your coding agents, built on top of a set of composable skills and some initial instructions that make sure your agent uses them." <Cite n={9} /> It is built by Jesse Vincent and Prime Radiant, under the MIT License. <Cite n={9} />

<CardGrid cols={2}>
  <InfoCard title="Superpowers as a mode or an agent" tone="bad">

Earlier versions of this page called Superpowers an autonomous agent or a "Superpower Mode" that removes approval prompts. The README describes no such mode. <Cite n={9} /> Approval prompts come from your [permission mode](/getting-started/permission-modes/).

  </InfoCard>
  <InfoCard title="Superpowers as a plugin of skills" tone="good">

Superpowers is a set of skills that trigger automatically. You do not need to run special commands. <Cite n={9} />

  </InfoCard>
</CardGrid>

### Install

```text
/plugin install superpowers@claude-plugins-official
```

This is the install command in the README. <Cite n={9} /> The README also gives a second way: <Cite n={9} />

```text
/plugin marketplace add obra/superpowers-marketplace
/plugin install superpowers@superpowers-marketplace
```

If you use more than one coding agent, install Superpowers separately for each one. <Cite n={9} /> To check the install, run `claude plugin list`. <Cite n={7} />

<Callout type="warning" title="Common mistake: old install commands">

`npm install -g @obra/superpowers` and `claude install superpowers` are not the install commands in the README. <Cite n={9} />

</Callout>

### The skills

The README lists 15 skills: <Cite n={9} />

| Group | Skills |
|---|---|
| Testing | `test-driven-development` |
| Debugging | `systematic-debugging`, `verification-before-completion`, `diagnosing-superpowers` |
| Collaboration | `brainstorming`, `writing-plans`, `executing-plans`, `dispatching-parallel-agents`, `requesting-code-review`, `receiving-code-review`, `using-git-worktrees`, `finishing-a-development-branch`, `subagent-driven-development` |
| Meta | `writing-skills`, `using-superpowers` |

The basic workflow has seven steps: `brainstorming`, `using-git-worktrees`, `writing-plans`, `subagent-driven-development` or `executing-plans`, `test-driven-development`, `requesting-code-review`, and `finishing-a-development-branch`. <Cite n={9} />

### What it gives a tester

- `test-driven-development` enforces RED-GREEN-REFACTOR: write a failing test, watch it fail, write minimal code, watch it pass, commit. It deletes code written before tests. <Cite n={9} />
- `systematic-debugging` is a 4-phase root cause process. `verification-before-completion` makes sure that a fix is real. <Cite n={9} /> Compare them with the example `analyze-rootcause` skill on [Skills & Commands](/extend/skills/).
- `subagent-driven-development` dispatches a fresh subagent for each task, with a review after each one. `executing-plans` runs every task in the current session, with one review of the whole branch at the end. <Cite n={9} />

<Callout type="note" title="Know what you adopt">

The README says: "Mandatory workflows, not suggestions." It also says that the agent may work on its own for a couple of hours at a time. <Cite n={9} /> Superpowers is a method for software development, not a test-only tool. Try it on one task before your team adopts it.

</Callout>

The README is also an example of what to read before you install. It describes optional telemetry: a logo that loads from the maintainers' site includes the version. Set `SUPERPOWERS_DISABLE_TELEMETRY`, or Claude Code's `DISABLE_TELEMETRY`, to turn it off. <Cite n={9} />

## Build a team marketplace

A marketplace file lives at `.claude-plugin/marketplace.json`. Its required top-level fields are `name`, `owner`, and `plugins`. <Cite n={10} /> Each plugin entry needs a `name` and a `source`. The `description` is the line shown in `/plugin`. <Cite n={11} />

Example: a QA team marketplace, in the format of the docs example. <Cite n={11} />

```json
{
  "name": "qa-team-plugins",
  "description": "Plugins for the QA team",
  "owner": { "name": "QA Team" },
  "plugins": [
    {
      "name": "qa-toolkit",
      "source": "./plugins/qa-toolkit",
      "description": "QA skills, qa-agent and sdet-agent, and file-protection hooks"
    }
  ]
}
```

- A relative `source` path resolves from the marketplace root, the folder that holds `.claude-plugin/`. <Cite n={10} />
- The entry `name` must be the same as the `name` in the plugin's `plugin.json`. <Cite n={11} />
- Other source types are `github`, `git-subdir`, `url`, `archive`, `npm`, and `command`. <Cite n={11} />
- Official and community names such as `claude-plugins-official` are reserved, and so are names that imitate them. <Cite n={10} />

Test it locally before you share it: <Cite n={11} />

```bash
claude plugin validate ./qa-team-plugins
claude plugin marketplace add ./qa-team-plugins
claude plugin install qa-toolkit@qa-team-plugins
claude plugin list
```
