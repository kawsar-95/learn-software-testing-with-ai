## The practice app

The app under test is a practice money-transfer app from a public SDET training course. It has bugs on purpose. Its README tells you not to deploy it and not to put it on the internet.

| Part | Technology | Address |
|---|---|---|
| REST API | Express, Sequelize, MySQL | `localhost:5000` |
| Web app | Next.js 15 | `localhost:3000` |

- The users have roles: Admin, Agent, Customer, and Merchant. An internal SYSTEM role also exists.
- The app has no balance column. The balance of an account is the sum of its credits minus the sum of its debits in a ledger table.
- A database table holds the daily and monthly limits of each customer.
- A customer can make 10 outgoing transactions per UTC day.

Most of the case study is about one feature: Send Money, a transfer from one customer to another.

### Skills and the command

A project skill is a folder with a `SKILL.md` file in `.claude/skills/<skill-name>/`. If you commit it, your team gets it too. <Cite n={1} /> A skill can have supporting files next to `SKILL.md`. <Cite n={1} />

- `pr-review` uses one supporting file, `reviewer-prompt.md`. The other six workspace skills have only `SKILL.md`.
- The two sub-project folders `api/.claude/skills/` and `web/.claude/skills/` are identical copies.
- `playwright.md` is a command file. Custom commands are merged into skills, and files in `.claude/commands/` still work. <Cite n={1} />

### Subagents

Each subagent runs in its own context window, with its own system prompt, tool access, and permissions. <Cite n={2} /> The `tools` field lists the tools that the subagent can use. <Cite n={2} /> The `skills` field preloads the full content of a skill into the subagent at startup. <Cite n={2} />

| Subagent | Model | Tools | Job |
|---|---|---|---|
| `qa-reviewer-agent` | Opus | Read, Grep, Glob, Skill, and read-only Serena tools. No Write, Edit, or Bash. | It marks each drafted bug APPROVED, FLAGGED, or REJECTED. Then it gives a gate: PASS or BLOCKED. |
| `test-executor-agent` | Sonnet | Read, Write, Glob, Grep, Bash, Skill | It runs prepared test cases. It preloads the `execute-test` skill with `skills:`. |

### The hook chain

`PreToolUse` hooks run before a tool call, and they can block it. <Cite n={3} /> An `mcp_tool` hook calls a tool on a configured MCP server. <Cite n={3} /> Hooks in `.claude/settings.json` apply to one project, and you can commit the file. <Cite n={3} />

This excerpt is the hook block of `./.claude/settings.json`, shortened. The Serena project name is a placeholder.

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Skill",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR/.claude/hooks/graphify-prehook.sh\"", "timeout": 45 },
          { "type": "mcp_tool", "server": "plugin:serena:serena", "tool": "activate_project",
            "input": { "project": "<project>", "session_id": "${session_id}" }, "timeout": 30 }
        ]
      }
    ]
  }
}
```

- The first hook runs a script. The script acts only for the `test-design` and `find-bug` skills. For any other skill, it exits with no output.
- The script queries the graphify knowledge graph. If the skill call has no arguments, it reads the start of the graph report. It sends the result back as `additionalContext`, with `permissionDecision` set to `allow`. `additionalContext` passes a string from the hook into the context of Claude. <Cite n={3} />
- The script also warns when the graph is older than the last commit.
- The second hook activates the Serena project. It has no skill filter, so it runs for every Skill call.

[Bug Hunting with a Review Gate](/case-study/bug-hunt/) shows what the hook gave to the bug hunt.

### MCP servers

Project-scoped MCP servers live in a `.mcp.json` file at the project root. <Cite n={4} /> In an interactive session, Claude Code asks for your approval before it uses a server from `.mcp.json`. <Cite n={4} />

| Server | Transport | Use in the workspace |
|---|---|---|
| `jira` | `http` | `understand-task` reads Jira tickets through it. |
| `playwright` | `stdio`, `npx -y @playwright/mcp@latest` | Browser automation. The `execute-test` skill forbids it: the executor uses only `curl` and `agent-browser`. |
| A MySQL server | `stdio`, a pinned package version, added on 2026-10-07 | SQL on the local database |

<Callout type="warning" title="The README and the config do not agree">

The README of the workspace lists only `playwright` and `jira` as project servers. It calls the database server a read-only server at user level. The `./.mcp.json` file also holds a MySQL server, and its config enables write actions. [What to Fix in the Setup](/case-study/lessons/) explains the fix.

</Callout>

`.claude/settings.json` holds the shared project settings. Your team checks this file into source control. <Cite n={5} /> In this workspace, the file holds only the hook chain. It has no `permissions` block.

## Take-aways

<Callout type="tip" title="The tutorial's own advice">

These points are the tutorial's own advice, not rules from the docs.

- Give each step of your QA work its own skill, and write each output to a file. Then the next step can read the file, and a reviewer can check it.
- Put a read-only reviewer with a PASS/BLOCKED gate between a draft and a report.
- Keep a session log of your prompts. Without it, you cannot show later how you got a result.
- Store your test results. A number in a README is not a test record.
- Read your own README against your config. In this workspace, one README statement was wrong and one was out of date.

</Callout>
